# Zebra Web Components

`packages/web-components` ships the design system as **Lit custom elements**
prefixed `zds-`, plus the CSS-variable token layer every Zebra package themes
from. It is a sibling of `packages/react-baseui`, not a layer under it — the
two share tokens, the icon font and the specs, and nothing else.

Read [references/code-style.md](references/code-style.md) before writing a
component — file shape, property conventions and token rules, with the
reasons behind them.

## Where everything lives

Three of these four are generated — nothing below is guessed at
implementation time.

| What | Where | Generated by |
|---|---|---|
| **Specs** | `specs/<component>/<component>.spec.json` + `.spec.md` | `zebra-figma-component-spec` skill |
| **Tokens (source)** | `tokens/` at the repo root — DTCG JSON, one file per collection mode | `zebra-figma-token-export` skill |
| **Tokens (CSS)** | `packages/web-components/src/tokens/*.css` | `scripts/build-tokens-css.mjs` — **never edit by hand** |
| **Icon font** | `packages/icons/` — `fonts/`, `icons.css`, `codepoints.json`, `icon-names.ts` | `zebra-figma-icon-font` skill |
| **Text fonts** | `src/tokens/fonts.css` — IBM Plex Sans from Google Fonts | derived from the font-family/weight tokens |
| **Components** | `src/components/<name>/<name>.ts` + `<name>.styles.ts` | you |
| **Stories** | `stories/<name>.stories.ts`, titled `Components/<Name>` | you |
| **Element manifest** | `custom-elements.json` | `pnpm run analyze` (cem) |

The spec is the contract, the component the implementation. Link them with a
`@spec` tag in the class JSDoc and a `Spec:` line atop the styles file:

```ts
/**
 * …
 * @spec specs/button/button.spec.json
 */
```

## Commands

```bash
cd packages/web-components
pnpm run tokens         # tokens/ -> src/tokens/*.css
pnpm run check          # tokens + typecheck + theming assertions — run before every commit
pnpm run storybook      # http://localhost:6007
pnpm run analyze        # regenerate custom-elements.json
```

`pnpm run check:theming` drives headless Chrome and asserts the theming
contract against `getComputedStyle` — not a unit test with a browser bolted
on. The bug class it guards against (a custom property substitutes where it
is *declared*, not where it is used) can't be modelled by hand, and an
earlier hand-rolled version of it passed while theming was in fact broken.

## Building a component from a spec

1. **Read the spec**, both files. `api` gives the properties, `anatomy` the
   parts, `variants` the table that drives most of the CSS, `issues` the
   things already known to be wrong — read those before you reproduce one
   faithfully.
2. **Create `src/components/<name>/`** with `<name>.ts` and
   `<name>.styles.ts` (see code-style.md), keeping the CSS sections in the
   spec's own axis order so the two can be read side by side.
3. **Bind only unprefixed semantic tokens.** A prefixed one (`--palette-*`,
   `--primitives-*`) is an internal layer; reaching into it couples the
   component to a level the theme system is allowed to move.
4. **Export it** from `src/index.ts`.
5. **Write `stories/<name>.stories.ts`**, one export per axis in the spec.
   Not optional — a component with no story is not done, and it is how the
   spec's variant table becomes something reviewable in Storybook.
6. **Run `pnpm run check`, then the visual audit below.** Both — they fail
   on disjoint things.
7. **Update the component table in `README.md`** with the element and a link
   to its spec.

Where the spec and the implementation cannot agree — a Figma binding that is
wrong, a value with no token — implement what the spec's `issues` section
says is intended, and leave a comment naming the issue. Do not silently do
something a reader would have to diff against Figma to discover.

## Visual audit

```bash
node .claude/skills/zebra-web-components/scripts/visual-audit.mjs button
node .claude/skills/zebra-web-components/scripts/visual-audit.mjs button --keep   # leave .audit/ in place
node .claude/skills/zebra-web-components/scripts/visual-audit.mjs button --full   # cross product, not one axis at a time
```

Sweeps each spec axis against the defaults and renders every specimen in four
theme panes (light, dark, `.ext-companion.mode-dark`, and light nested in
dark), then asserts what only exists once painted: no collapse to zero
height, the size axis actually changing size, no label sharing its
background's colour, icon glyphs drawing, dark mode reaching the component
(not just the page), and nested `mode-light` returning to light.

**It prints a screenshot path. Open it.** The assertions catch collapse,
invisibility and broken theming; they cannot tell you a button is simply the
wrong shape — two cross-component bugs on Navigation Rail passed every
per-component check on this design system and were caught only by looking.

[references/visual-audit.md](references/visual-audit.md) explains what each
assertion means when it fails and how to extend the set.

Two warnings are expected on a faithful Button, not regressions:

- **contrast below 4.5:1** — real WCAG shortfalls in the Figma palette,
  recorded in the spec's `issues`. Compare the count against the spec before
  treating a change as new.
- **an axis that is not a property** — a spec's `state` axis (hover, pressed,
  focus) is CSS, never a property; the audit can't tell that apart from a
  property nobody wired up.

## Icons

An icon is a **font glyph**, never an SVG and never a Figma node.

```html
<zds-icon name="alarm" label="Alarm"></zds-icon>   <!-- labelled, exposed to AT -->
<zds-icon name="add"></zds-icon>                    <!-- decorative, aria-hidden -->
```

- **`icons.css` must be loaded once in the host page.** `@font-face` is
  document-scoped and reaches into shadow roots; the `.zds-icon-*` class
  rules do not. `<zds-icon>` therefore looks the character up from
  `codepoints.ts` itself and only sets the family.
- **The glyph takes `currentColor` and `1em`** — the entire reason icons ship
  as a font. Never give an icon its own colour token inside a component.
- **`rounded` / `sharp` is a family swap, not a different glyph** — both
  share codepoints. A component that pins one (Button pins it from its own
  `shape`) should say so in a comment.

Check a name against `packages/icons/codepoints.json` before using it. Nine
icons have no glyph at all (stroked paths, non-square viewBoxes) and are
listed in `inventory.json`; naming one renders nothing, silently.

## Theming

A class on any ancestor, in the light DOM, cascading into every shadow root
below it:

```html
<div class="ext-companion mode-dark"> … </div>
```

`ext-*` selects a brand extension, `mode-*` light/dark, `bp-*` a size and
typography mode. There is no JavaScript theme provider and nothing
re-renders. A component that reads only semantic tokens gets all of this for
free; one that hard-codes a colour opts out of it permanently.

## Committing

Conventional Commits, enforced for release versioning. Scope with the
component or the package:

```
feat(button): add gradient and text-gradient flavours
fix(icon): look the glyph up in the component so shadow roots resolve it
```

`docs:`, `chore:`, `test:`, `refactor:` and `style:` do not bump a version;
`feat:` minor, `fix:`/`perf:` patch, `BREAKING CHANGE:` major. Full table in
`CONTRIBUTING.md`.
