The governing instructions for anyone building with Zebra, people and agents alike. It covers the rules, the token vocabulary and the component inventory, each at its smallest useful level. Each section points to the file that holds the detail.

When this file and a detailed source disagree, the detailed source wins: the token export for values, the component spec for anatomy and props. Fix this file to match.

---

## 1. Principles

1. **Tokens, never values.** Every colour, size, radius, space, stroke, shadow and type value comes from a semantic token. A value with no token is a gap to report, not something to inline.
2. **Semantic tokens only.** Components read the unprefixed semantic layer (`--surface-card`, `--interactive-primary-background-default`). `--primitives-*` and `--palette-*` are internal layers the theme system moves underneath you.
3. **Library first.** Build from existing components before writing new UI. A control that already exists (button, chip, input, menu) is used, never re-drawn.
4. **Themes cascade; nothing re-renders.** Light/dark, brand and density are classes on an ancestor. There is no theme provider, context or hook.
5. **Icons are font glyphs.** An icon is a name from the icon font that takes `currentColor` and the inherited size. It is never an SVG, an image or an emoji.
6. **Accessible by default.** Text pairs meet WCAG AA, every interactive element has a visible focus ring (`focus/outline`) and an accessible name, and motion respects reduced-motion.
7. **Code and Figma are one system.** Specs come from Figma. Experiments start in code and go back to Figma for review before they get a spec.

*More principles and the system's ideology will be added here.*

## 2. Shape inheritance

Shape is decided once, at the page, and flows down. This is the rule to internalise: most designs never mix shapes, so one declaration at the top covers the whole screen.

- **Set shape at the page level.** A design is rounded or sharp throughout; the page (or the screen's root container) declares it once and everything inside follows. A second shape on the same page is the exception, not a per-component choice.
- **A container flagged sharp makes everything inside it sharp,** unless a child is explicitly given another shape. Nested buttons, chips, inputs, cards, badges, menus, tooltips and progress indicators all take their sharp variant.
- **A container flagged rounded makes everything inside it rounded,** under the same rule.
- **An explicit shape on a child always wins** over the inherited one — and opts that child out of the page's choice, so fix a shape only where the design genuinely departs from the page.
- **Overriding a radius is not setting a shape.** A composition may take a different `--radius-*` to fit its layout; as long as its children's shape stays unset, they keep inheriting the page shape.
- `full` (pill) is a deliberate choice on a single element such as an icon button. It is never inherited. Under a rounded parent, children use `rounded`; under a sharp parent, they use `sharp`.
- **Defaults follow the rounded contour** (Button and Icon Button default `medium`/`rounded`, matching Figma), so a sharp surface sets shape explicitly rather than relying on defaults.
- Components spell shape differently: `shape="rounded" | "sharp"`, `rounded: boolean`, or Figma's `Rounded=true/false`. The rule is the same for all of them.
- **In code,** a container passes its shape to its children and a child's own prop overrides it. Radii read `--radius-*` tokens and collapse to `--radius-none` when sharp.
- **In Figma,** nested instances are set to the matching `Rounded`/`Shape` variant of their parent.

## 3. Tokens

**Source of truth:** `tokens/` (DTCG JSON exported from Figma) and `tokens/manifest.json` for collections, modes and extensions.
**CSS:** `packages/*/src/tokens/*.css`, generated by `pnpm run tokens`. Never edit it by hand.
**Naming:** Figma `group/sub/name` becomes CSS `--group-sub-name`, e.g. `interactive/primary/background/default` becomes `--interactive-primary-background-default`.

### Layers

| Layer | Collection | Modes | Use it? |
|---|---|---|---|
| Primitives | `primitives` | Value | No. Raw scale, hidden. |
| Palette | `palette` | Light, Dark | No. Theme layer under semantics. |
| Semantics | `semantics` | Base | **Yes.** Colour roles. |
| Size | `size` | Desktop, Mobile, Tablet, Desktop Compact | **Yes.** Space, radius, control, stroke, shadow, motion. |
| Typography | `typography` | Desktop, Tablet, Mobile, Desktop Compact | **Yes.** Type steps. |

**Extensions** override a parent collection and change nothing else: `companion` (palette), `target` (primitives and palette), `condensed` (size and typography).

### Colour (semantics)

| Family | Tokens |
|---|---|
| `surface/` | `page`, `section`, `card`, `subtle`, `brand`, `inverse`, `overlay`, `shade`, `tooltip`, `track`, `info`, `success`, `warning`, `error`, `gradient/start·end` |
| `foreground/` | `primary`, `secondary`, `tertiary`, `disabled`, `inverse`, `link`, `on-strong`, `on-light`, `info`, `success`, `warning`, `error`, `cursor`, `gradient/start·end` |
| `border/` | `default`, `subtle`, `strong`, `inverse`, `focus`, `disabled`, `transparent`, `info`, `success`, `warning`, `error`, `gradient/start·end` |
| `interactive/<flavour>/` | Flavours `primary`, `secondary`, `neutral`, `subtle`, `ghost`, `positive`, `destructive`, `inverse`, plus `selection`. Each has `background/` and `border/` across `default`, `hover`, `pressed`, `focused`, `selected`, `disabled`, and `foreground/` (`default`, `disabled`). |
| `feedback/<status>/` | `info`, `success`, `warning`, `error`, `neutral`, each with `background/strong`, `background/subtle` and `foreground` |

### Size

| Group | Scale |
|---|---|
| `space/` | `none`, `3xs`, `2xs`, `xs`, `sm`, `md`, `lg`, `xl`, `2xl`, `3xl`, `4xl`, `5xl`; layout: `card`, `gutter`, `section`, `page`; negative: `neg/xs`–`neg/xl` |

### Typography

| Role | Steps |
|---|---|
| `display` | large, medium, small |
| `heading` | large, medium, small |
| `title` | large, medium, small |
| `body` | large, medium, small, xsmall |
| `label` | large, medium, small |
| `indicator` | medium, small |

Each step carries `font family`, `font size`, `font weight`, `line height` and `letter spacing`, e.g. `--body-medium-font-size`.

### Theming classes

Put these on any ancestor (they work in both packages and on plain HTML):

- `mode-light` / `mode-dark` switch the palette.
- `ext-companion` and `ext-condensed` apply a brand or density extension.
- `ext-<project>` applies a project's own theme. It is generated from a small file of overrides by `npx zebra-theme` (in `@zebra-design-system/tokens`), the same way the shipped extensions are built. A theme changes values, never names.
- `bp-*` applies a size and typography mode.

## 4. Components

Three libraries share the tokens, the icon font and the specs, and no component code:

- **React:** `packages/react-baseui` (Base UI primitives). Storybook runs on `:6008`.
- **Web components:** `packages/web-components` (Lit, `zds-*`). Storybook runs on `:6007`.
- **Zeta Web (legacy):** `packages/zeta-web` (Lit, `zeta-*`), refined against the same specs in its own house style. Storybook runs on `:6006`.

**Spec for each component:** `specs/<name>/<name>.spec.md` (readable) and `.spec.json` (contract). Read the spec before building or changing a component, including its `issues` section.

Interaction states such as hover, pressed and focus are CSS states, never props, even where Figma models them as variants.

## 5. Patterns

The UX patterns are the rules for how screens are composed and behave. They have the same authority as this file: this file and the specs say what things look like, and the patterns say how screens are put together.

The rules name no component and no token, so a product on any component system can follow them. They ship as `@zebra-design-system/patterns`, which installs with each component library.

| Pattern | Covers |
|---|---|
| 01 Screen composition | Composing the screen, the shell, messages, actions, finding things, content, overlays, flows, forms |
| 02 Navigation and flow | Structure, global and local navigation, back and exit, deep links, wizards, task loops, sign-in |
| 03 Controls and interaction | Buttons, choices, text entry, dates, selection, menus, saving, undo, gestures, scanning, motion |
| 04 States, feedback and recovery | Loading, empty, error, success, offline, sync, permissions, sessions, device states, severity |
| 05 Sizes and devices | Size classes, grids, how components change, overflow, density, form factors, input modes |
| 06 Accessibility | The floors under every other rule: contrast, targets, focus, names, announcements, reflow, time limits |
| 07 Content and copy | Voice, labels, messages, errors, terms, numbers, dates and units, translation |
| 08 Visual foundations and theming | Colour roles, states, themes, type, space, shape, elevation, icons, brand, re-theming |
| 09 AI in the interface | Where AI is offered, suggestions, marking and sources, confidence, acting for someone, failures |
| 10 Data display | Choosing the form, tables, lists, records, status and numbers in data, charts, live data, maps |

- Start at the patterns' `README.md`. It says which files a task needs.
- Each file holds numbered rules. The bold sentence is the rule. Cite one by its number: `patterns 4.21` is rule 21 of file 04.
- Accessibility minimums come first, then a product's own shell and established patterns, then the more specific rule.
- A rule that starts "By default" may be overridden by a project.
- `zebra.md` maps each pattern word to a Zebra component or token.
