Zebra Design System · for builders and designers

From zero to an on-system screen with Claude Code

One install gives Claude the Zebra components, tokens and skills. After that you never touch a package manager: you describe the screen — in words, a Figma link, or a photo of a sketch — and Claude builds it from the real library, themed for light and dark from the first render.

1Install the plugin — once per machine

This is the only step that happens in a terminal. Open one, and paste these two lines (your GitHub account needs access to the Zebra repo — ask the design system team if a step fails with a permission error):

claude plugin marketplace add "https://github.com/multiplayer-studio/zebra-design-system.git#main"
claude plugin install zebra-design-system@zebra-design-system

From here on, everything is a conversation with Claude. The plugin gives it:

  • skill builder-start — where a developer begins in a repo: one short question picks the path, and the repo's coding style is recorded once in a zebra-build folder.
  • skill builder-figma-to-code — turns a Figma design into working screens, in a repo on the Zebra packages or one that keeps its own component library.
  • skill builder-handoff-to-code — builds a designer's handoff package exactly as specified.
  • skill builder-ui — designs screens from a written brief.
  • skill builder-migrate — moves an existing app onto the system, a screen or a component at a time.
  • skill builder-design-check — measures a built screen against its design and lists every difference.
  • skill designer-prototype — builds shareable prototypes as claude.ai pages.
  • skill designer-project-onboarding — sets a project up once, from nothing, a Figma design or a codebase, and saves its context in a zebra-context folder for every later prototype.
  • skill designer-theme — gives a project its own brand colour and font, checked for contrast in every mode. Works with the plugin alone.
  • skill designer-handoff — turns a finished prototype into a build spec for developers, covering what changed since the last handoff.
  • skill shared-ux-patterns — applies Zebra's rules for how screens are composed and behave.
  • skill shared-ux-audit — audits any product against those rules, whatever it is built with.
  • command /zebra-setup — wires any project to the system and fixes what's missing.
  • command /zebra-theme — themes the project from a brand colour or font.
  • command /zebra-components — answers "what exists?" from the official catalog.

Every skill reads the system's design contract before touching anything, so the output follows Zebra's rules, not Claude's general taste.

Auditing a product that isn't built with Zebra? Install only the rules and the two UX skills: claude plugin install zebra-patterns@zebra-design-system.

2Fastest path: a shareable prototype

No app, no setup knowledge needed. Make an empty folder, open Claude Code in it, and describe the idea. The designer-prototype skill installs what it needs, builds the page from real components, and publishes it as a private claude.ai link you can share for review.

You say"Set this folder up for Zebra prototyping, then prototype a parcel-tracking dashboard — status cards, a shipments table, a details panel — and publish it as an artifact I can share."

In an empty folder Claude first asks how you want to start: Free exploration, Figma reference or From a repo. With a Figma reference it matches the design's variants, spacing and typography, and asks you to choose wherever the design and the system clearly differ.

Keep talking to refine it — "make the table denser", "show the empty state", "try it in dark" — and Claude republishes to the same link each time.

Primary action Outline Text These are the real components, rendered live on this page — switch your theme and they re-theme. Your prototype is made of the same parts.

3A fresh app — pick your technology

Three component libraries share the same designs, colours and icons; which one you use depends on the app's technology. You don't install anything yourself — name the choice in your prompt and Claude scaffolds, installs and verifies with /zebra-setup. Not sure which? Say so, and Claude will ask the right questions.

React

Pick when the team builds (or wants to build) in React — the most common choice for new product work.

You say"Scaffold a new React app wired to the Zebra Design System, then run /zebra-setup to verify everything."

Web Components

Pick for any other stack, or none — these components work in plain web pages and inside other frameworks.

You say"Scaffold a new app on Zebra's web components, then run /zebra-setup to verify everything."

Zeta Web

Pick only when the team already builds on the legacy zeta-* components.

You say"Set this app up with Zeta Web from the Zebra system and verify the theming."

Claude installs the packages straight from the Zebra repo — no npm account, no registry. To stay on an exact version or take an update later, just ask: "pin the Zebra packages to the current version" or "update the Zebra packages".

4An existing project or boilerplate

Open Claude Code in the project and run one command:

You type/zebra-setup

It checks whether the Zebra packages are installed (and installs the right ones for your stack if you confirm), adds the two theme imports apps need, renders a component and flips dark mode to prove theming really reaches it, installs the skills, and ends with a status table — each line OK or fixed. If something in the app breaks in dark mode, it finds the hard-coded colour causing it rather than patching the symptom.

5Build from a Figma design

skill builder-figma-to-code

Zebra's Figma library and its code components are the same system, so a Figma screen is a translation job, not a reinvention. Connect Figma once (in Claude Code: Settings → Connectors → Figma, or ask Claude "connect Figma for me"), then paste the frame's link:

You say"Build this screen in my app: figma.com/design/…?node-id=… — exactly as designed."

  • Every Figma component becomes the real installed component, with the same variant choices the designer made.
  • Colours, spacing and text styles map to the system's tokens — nothing is eyeballed.
  • A frame the designer set to dark or to a brand stays that way in code.
  • Anything that doesn't map — a colour with no token, a part with no component — is flagged in Claude's report instead of silently invented. Pass that report to the design system team; it's how the system improves.

6Vibe a design from a brief

skill builder-ui

No design yet? Describe what the screen is for and let the system make it look designed. Say as much or as little as you like — the system's design contract fills in whatever you don't specify.

You say"Design a warehouse check-in flow: a scan step, an exceptions list, a confirmation. Sharp corners, works in dark, one clear primary action per view."

  • Claude composes from the official components and type scale — it won't hand-draw a button or pick a random colour.
  • Useful words to steer with: the shape ("rounded" or "sharp"), the mood ("dense" or "calm"), the one action that matters most on each screen.
  • Review in both themes: ask "show it in dark" — if it's built right, dark is free.

7From a sketch or screenshot

skill builder-ui

A whiteboard photo, a napkin sketch, a screenshot of an old tool or another product — drag the image into the Claude Code chat and ask for it on-system:

You say"Rebuild this on the Zebra system — keep the layout and intent, but replace every element with our components, colours and type."

  • Each drawn element maps to the nearest real component; the sketch becomes a working, themed screen rather than a pixel copy.
  • Claude names anything it couldn't map, so you know what was interpreted.
  • This is also the fastest way to modernise screenshots of legacy UI.

8While you work

  • command /zebra-components — ask what exists before asking for something new: "is there a stepper?", "what flavours does Button have?" Answers come from the official catalog for your installed version, never from memory.
  • Review every screen in both themes — ask Claude to "toggle dark mode" on what it just built. Something only breaking in dark means an off-system value sneaked in.
  • After Claude updates the Zebra packages, ask it to "refresh the Zebra skills in this project" so the local copies match.
  • When Claude reports a gap — a missing component, token or icon — forward it to the design system team. Those reports are the system's feedback channel.
