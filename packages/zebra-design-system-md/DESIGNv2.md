# Zebra Design System

## Overview

Zebra (Zeta) is a utility-first UI language for enterprise, retail and field-operations software. It runs on rugged handhelds, tablets, POS terminals and desktops, often with gloves, scanners and glare. The tone is calm and precise: neutral surfaces, one blue accent for action, and color reserved for meaning. Density is chosen per device, not per taste.

This file is the compact, agent-facing view. Detail lives next to it, and the higher source wins on conflict:

1. `tokens.json`: all values. The front matter above is a trimmed copy; anything missing (chart colors, selection colors, secondary and inverse interactive families, gradients, `focused` and `selected` states) is read from there.
2. `icons.json`: all icon names. Never invent one.
3. `components/*.md`: anatomy, token bindings and state matrices per component.
4. `DESIGN.md`: form-factor rules, accessibility baselines, motion.

Token names here are `tokens.json` paths joined with `-` (`color.light.surface.card` is `surface-card`). Dark theme tokens repeat the same names with a `dark-` prefix.

## Colors

One blue accent, neutral surfaces, semantic feedback hues. Components bind to semantic tokens only, never to raw hex.

- **Primary (`primary`, #1f69ff):** the single high-emphasis action per view region, links and the focus ring.
- **Neutral (`neutral`, #f3f6fa):** page canvas. Content sits on `surface-section` (white) or `surface-card`.
- **Foreground:** `foreground-primary` for text, `foreground-secondary` for supporting text, `foreground-disabled` for placeholders and inactive content.
- **Feedback:** `feedback-{success,warning,error,info}-{background,foreground}`. Always paired with an icon and text, never color alone.
- **Interactive:** `interactive-<family>-<background|foreground|border>-<state>` with families `primary`, `positive`, `destructive`, `ghost`, `neutral`, `subtle` and states `default`, `hover`, `pressed`, `disabled`.
- **Focus:** `focus-ring` is a 2px ring (`stroke-thick`) with an offset, on every interactive element.
- **Dark theme:** swap `X` for `dark-X`. Re-check contrast in both themes.

## Typography

One family, **IBM Plex Sans**, in six roles: `display` (light, 36-52px), `heading` (regular, 24-32px), `title` (medium, 12-20px), `body` (regular, 12-20px), `label` (medium, 12-16px) and `indicator` (10-12px, counts and badges). Sizes are `large`, `medium`, `small`, plus `xsmall` for body. Values are the same on every device tier. Buttons and tabs use `label-*`, running text uses `body-*`, card and dialog headings use `title-*`.

## Layout

Spacing is a fixed scale (`2xs` to `2xl`) plus named roles (`page`, `section`, `card`, `gutter`). Take values from the tokens; never compute them.

Device tiers change layout, not token values:

| Tier | Used for | Layout |
|:---|:---|:---|
| `mobile` | wearables, rugged handhelds | Single column, bottom-anchored primary action, thumb-zone controls |
| `tablet` | tablets, POS | Two-pane and master-detail |
| `desktop` | pointer-first | Multi-pane, tables, side navigation, 1200px content width |
| `desktop compact` | dense pointer-only screens | Same as desktop, 840px content width. Never where touch is the primary input |

Controls are `control-sm` (36px), `control-md` (40px) or `control-lg` (48px). The minimum hit area is `control-target-min` (40px). A smaller control extends its hit area to that minimum on touch displays.

## Elevation & Depth

Depth comes mostly from tonal layers (`surface-page` < `surface-section` < `surface-card`) and hairline borders (`border-default`, `stroke-thin`). Shadows are reserved for floating surfaces such as menus and popovers, using `shadow-soft` or `shadow-hard` at the `size.shadow.small` or `size.shadow.medium` offsets and blur in `tokens.json`. Modal dialogs sit over `overlay-scrim`.

## Shapes

Corners follow the tier's `shape` value in `tokens.json`: `sharp` on `mobile`, `rounded` elsewhere. Small controls use `rounded-element-sm`, floating surfaces `rounded-element-md`, containers `rounded-sm`. Badges and avatars use `rounded-pill`. Sharp means `rounded-none`. Do not mix sharp and rounded corners in one view.

## Components

Each component has one file in `components/`. If a component is not listed here, it does not exist: propose it first. The tokens in the front matter cover the common case; borders, focus rings, gradient flavours and all other states are in the component file.

| Component | Category | Role |
|:---|:---|:---|
| `avatar` | Data Display | Person or entity as initials, photo or glyph, with presence status |
| `button` | Action | One action. Flavours: primary, positive, negative, outline, outline-subtle, text, subtle, gradient, text-gradient |
| `card` | Data Display | Bounded surface grouping heading, media, body and footer actions |
| `checkbox` | Data Entry | Independent on, off or partial option |
| `dialog` | Feedback | Interrupts the flow to request a decision |
| `divider` | Layout | Thin line separating content groups |

Button states: hover and pressed change only the background (`button-primary-hover`, `button-primary-pressed`). Disabled uses the `disabled` background and foreground and ignores input.

## Iconography

Icons are looked up in `icons.json` by exact name. A missing name is a gap to report, not a reason to pick a similar glyph. Sizes follow `size.control.icon.{sm,md,lg}` (16, 20, 28px).

## Do's and Don'ts

- Do use one high-emphasis button (`button-primary`) per view region.
- Do reference token names; never hardcode a color, size or radius. If a token is missing, stop and report the gap.
- Do meet WCAG 2.2 AA: 4.5:1 text contrast, 3:1 for icons, borders and focus rings, in both themes.
- Do show a visible focus ring and keep every target at least 40px.
- Do pair error, warning, success and info with an icon and text.
- Do respect `prefers-reduced-motion`. Motion explains a state change and is never decorative (see `DESIGN.md` section 5).
- Don't convey meaning with color alone, including selected and checked states.
- Don't use `desktop compact` where touch is the primary input.
- Don't add variants, states or anatomy that are not in the component file.
- Don't reference web components, framework wrappers or design-tool layer names in specs.
